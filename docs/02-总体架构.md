# 总体技术架构

## 1. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 客户端 | 微信小程序原生框架（TypeScript + Skyline/glass-easel 可选） | 包体小、审核路径清晰、可直接使用微信登录/语音能力 |
| 实时通信 | WebSocket（小程序 `wx.connectSocket`） | 游戏状态推送必须实时；轮询不可行 |
| 后端 | Node.js + NestJS（或 Koa）+ ws / socket.io | 单语言栈、事件驱动模型契合房间广播 |
| 房间/游戏状态 | Redis（内存态 + 持久化快照） | 房间是短生命周期高频读写数据 |
| 持久化 | MySQL（用户、对局记录、战绩） | 结构化查询、战绩统计 |
| 语音 | 腾讯云 TRTC 小程序 SDK（详见 04-语音方案） | 与微信生态最兼容 |
| 部署 | 云托管（微信云托管）或轻量云服务器 + Docker | 云托管免运维且内网直连微信 API |

> 备选：如果想降低后端复杂度，可用 **微信云开发（TCB）+ 实时数据推送**，但云开发的实时能力延迟与连接数受限，房间制强实时游戏建议自建 WebSocket 服务。

## 4. 游戏状态机 (GameFSM)

**核心原则：服务端权威。客户端只发意图，所有规则判定在服务端完成，私密信息按角色定向下发。**

```
LOBBY(准备) → NIGHT(夜晚看牌确认) → TEAM_PICK(队长组队)
   → TEAM_VOTE(全员投票) ─否决→ TEAM_PICK(下任队长, voteRound+1)
   │                      └5次否决→ GAME_OVER(邪恶胜)
   └通过→ QUEST(队员出票) → 判定 → {任务进度更新}
        → 好人3胜 → ASSASSIN(刺杀) → GAME_OVER
        → 坏人3胜 → GAME_OVER
        → 否则 → TEAM_PICK(下一轮)
```

状态数据结构（Redis 中，key: `game:{roomId}`）：

```typescript
interface GameState {
  roomId: string;
  phase: 'LOBBY'|'NIGHT'|'TEAM_PICK'|'TEAM_VOTE'|'QUEST'|'ASSASSIN'|'GAME_OVER';
  players: PlayerState[];        // 座位序、openid、角色、在线状态
  roleConfig: RoleId[];          // 本局角色板子
  questIndex: number;            // 当前第几轮任务 0-4
  questResults: ('S'|'F')[];     // 已完成任务结果
  leaderIndex: number;           // 当前队长座位
  voteRound: number;             // 本轮第几次组队(1-5)
  currentTeam: number[];         // 被提名队员座位
  teamVotes: Record<seat, boolean>;   // 组队投票(公开)
  questVotes: Record<seat, 'S'|'F'>; // 任务出票(仅统计后公开数量)
  history: RoundRecord[];        // 每轮完整记录，供复盘
  deadline: number;              // 当前阶段截止时间戳(服务端计时)
  version: number;               // 状态版本号，客户端用于乱序丢弃
}
```

## 5. WebSocket 协议设计

统一消息格式：`{ type, seq, data }`，服务端推送带 `version` 做幂等。

### 客户端 → 服务端（意图）
| type | 说明 |
|---|---|
| `room.join` / `room.leave` / `room.ready` | 房间操作 |
| `game.start` | 房主开局 |
| `night.confirm` | 夜晚看牌确认 |
| `team.pick` | 队长提交队伍 |
| `team.vote` | 组队投票 {approve} |
| `quest.vote` | 任务出票 {success} |
| `assassin.kill` | 刺客刺杀 {targetSeat} |
| `heartbeat` | 心跳（15s） |

### 服务端 → 客户端（状态）
| type | 说明 |
|---|---|
| `room.sync` | 房间成员/准备状态全量同步 |
| `game.sync` | **按视角过滤后的**游戏状态（每人收到的不同）|
| `game.secret` | 定向私密信息（角色牌、夜晚视野），仅发一次+重连补发 |
| `phase.change` | 阶段切换 + 截止时间 |
| `game.over` | 结算数据（全量身份公开） |

### 视角过滤（防作弊关键）
- 角色、夜晚视野只通过 `game.secret` 定向下发，任何广播消息不含他人身份
- 任务出票只广播"成功/失败票数"，不广播个人票
- 客户端不做任何规则计算，防止逆向抓包获取额外信息

## 6. 断线重连

1. 客户端持 JWT 重连 → 网关校验后查 Redis 是否在局中
2. 在局中 → 补发 `game.sync`（当前视角状态）+ `game.secret`（自己的身份）
3. 座位保留 120s（Redis 记录 `disconnectAt`），超时且在 LOBBY 阶段则踢出；游戏中不踢出，按超时默认策略代投
4. 服务端计时器统一在服务端触发，客户端倒计时仅做展示

## 8. 扩展性与容量

- 单房间 ≤10 人 + 旁观，状态极小；单 Node 进程可承载数千房间
- 水平扩展：网关按 `roomId` 一致性哈希路由到房间所在进程（或用 Redis Pub/Sub 跨进程广播）
- MVP 阶段单实例 + Redis 即可，不必过度设计

## 9. 合规注意

- 小程序类目建议：**休闲游戏**（需注册小游戏类目或社交-笔记等，实时语音有类目门槛，见 04 文档）
- 游戏类小程序需软著 + 版号相关要求评估（无内购的休闲对战小程序按小游戏流程申报；若做成"工具化桌游助手"形态可规避部分门槛，需在产品定位时确认）
- 用户昵称头像获取遵循最新微信隐私接口规范（`getUserProfile` 已收回，使用头像昵称填写能力）
