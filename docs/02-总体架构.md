# 总体技术架构（H5 版）

> 产品形态已确定为 **移动端 H5 网页游戏**（主要在微信内以链接方式传播打开），不做小程序。
> 核心收益：实时语音使用浏览器标准 WebRTC，无微信资质门槛，个人开发者可完整落地。

## 1. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 客户端 | Vue 3 + TypeScript + Vite（移动端 H5，单页应用） | 生态成熟、包体可控、组合式 API 适合状态机驱动的界面 |
| 状态管理 | Pinia | 轻量，配合 WS 推送做单向数据流 |
| 实时通信 | 原生 WebSocket（wss） | 游戏状态推送必须实时 |
| 后端 | Node.js + Fastify + ws（不用 NestJS：装饰器元数据与 ESM/tsx/vitest 工具链摩擦大，纯函数状态机不需要 DI 容器） | 单语言栈、事件驱动契合房间广播 |
| 房间/游戏状态 | Redis | 短生命周期高频读写 |
| 持久化 | MySQL（用户、对局记录、战绩） | 结构化查询 |
| 语音 | 自建 LiveKit（首选）或腾讯云 TRTC Web SDK（详见 04-语音方案） | WebRTC SFU，无平台资质门槛 |
| 部署 | 云服务器 + Docker Compose（nginx / server / livekit / redis / mysql） | 一台轻量服务器起步 |

基础设施前提：一个已备案域名 + HTTPS 证书（`getUserMedia` 与 wss 均强制 HTTPS）。

## 3. 前端工程结构

```
web/
├── src/
│   ├── views/          # Home(封面) / Room(大厅) / Game(游戏桌面) / Result(结算) / Rules
│   ├── components/     # SeatRing / RoleCard / VotePanel / QuestTrack / VoiceBar / PhraseChips
│   ├── stores/         # roomStore / gameStore / userStore
│   ├── services/       # ws.ts(重连+心跳+消息路由) / api.ts / voice.ts(LiveKit 封装)
│   ├── router/
│   └── assets/         # SVG 图标、角色插画、音效
└── vite.config.ts
```

前端要点：
- 视口适配：`viewport-fit=cover` + `dvh` 单位 + 安全区 `env(safe-area-inset-*)`；设计稿 390px 基准，尺寸用 `rem`（postcss 按 390 换算）
- 微信内嵌浏览器兼容：iOS ≥14.3 支持 WebRTC；麦克风授权必须由用户手势触发；用 `navigator.wakeLock` 防息屏（不支持时降级为提示保持亮屏）
- 身份等敏感界面禁止进入浏览器前进/后退缓存造成的泄露：路由守卫 + 页面隐藏时遮罩（`visibilitychange`）

## 4. 用户体系（无微信登录）

- 首次进入生成设备匿名账号：`localStorage` 存 `uid + token`（服务端签发 JWT）
- 用户只需填昵称、选预设头像（本地记住）；不接微信 OAuth（需要服务号资质，刻意绕开）
- 同一 uid 断线重连凭 JWT 恢复座位；换设备即新账号（朋友局场景可接受）

## 5. 游戏状态机 (GameFSM)

**核心原则不变：服务端权威。客户端只发意图，规则判定全部在服务端，私密信息按角色定向下发。**

```
LOBBY(准备) → NIGHT(夜晚看牌确认) → TEAM_PICK(队长组队)
   → TEAM_VOTE(全员投票) ─否决→ TEAM_PICK(下任队长, voteRound+1)
   │                      └5次否决→ GAME_OVER(邪恶胜)
   └通过→ QUEST(队员出票) → 判定 → {任务进度更新}
        → 好人3胜 → ASSASSIN(刺杀) → GAME_OVER
        → 坏人3胜 → GAME_OVER
        → 否则 → TEAM_PICK(下一轮)
```

状态数据结构（Redis，key: `game:{roomId}`）：

```typescript
interface GameState {
  roomId: string;
  phase: 'LOBBY'|'NIGHT'|'TEAM_PICK'|'TEAM_VOTE'|'QUEST'|'ASSASSIN'|'GAME_OVER';
  players: PlayerState[];        // 座位序、uid、角色、在线状态
  roleConfig: RoleId[];          // 本局角色板子
  questIndex: number;            // 当前第几轮任务 0-4
  questResults: ('S'|'F')[];     // 已完成任务结果
  leaderIndex: number;           // 当前队长座位
  voteRound: number;             // 本轮第几次组队(1-5)
  currentTeam: number[];         // 被提名队员座位
  teamVotes: Record<seat, boolean>;   // 组队投票(公开)
  questVotes: Record<seat, 'S'|'F'>; // 任务出票(仅统计后公开数量)
  history: RoundRecord[];        // 每轮完整记录，供复盘与战局记录抽屉
  settings: RoomSettings;        // 开局时冻结的建房配置(见 03 文档第 8 节)
  speaker?: { seat: number; deadline: number }; // 轮流发言模式下的当前发言者
  deadline: number;              // 当前阶段截止时间戳(服务端计时)
  version: number;               // 状态版本号，客户端乱序丢弃
}
```

## 6. WebSocket 协议设计

统一消息格式：`{ type, seq, data }`，服务端推送带 `version` 做幂等。

### 客户端 → 服务端（意图）
| type | 说明 |
|---|---|
| `room.join` / `room.leave` / `room.ready` | 房间操作 |
| `game.start` | 房主开局 |
| `night.confirm` | 夜晚看牌确认 |
| `team.pick` | 队长提交队伍 |
| `team.vote` | 组队投票 {approve} |
| `quest.vote` | 任务出票 {success} |
| `assassin.kill` | 刺客刺杀 {targetSeat} |
| `heartbeat` | 心跳（15s） |

### 服务端 → 客户端（状态）
| type | 说明 |
|---|---|
| `room.sync` | 房间成员/准备状态全量同步 |
| `game.sync` | **按视角过滤后的**游戏状态（每人收到的不同） |
| `game.secret` | 定向私密信息（角色牌、夜晚视野），仅发一次+重连补发 |
| `phase.change` | 阶段切换 + 截止时间 |
| `voice.policy` | 语音权限位（详见 04-语音方案） |
| `speaker.turn` | 轮流发言模式：当前发言座位 + 截止时间 |
| `game.paused` | 玩家中途退出导致的等待/作废决策提示 |
| `game.over` | 结算数据（全量身份公开） |

### 视角过滤（防作弊关键）
- 角色、夜晚视野只通过 `game.secret` 定向下发，广播消息不含他人身份
- 任务出票只广播成功/失败票数，不广播个人票
- 客户端不做任何规则计算，抓包无法获得额外信息

## 7. 断线重连

1. 客户端持 JWT 重连 → 网关校验后查 Redis 是否在局中
2. 在局中 → 补发 `game.sync`（当前视角状态）+ `game.secret`（自己的身份）
3. 座位保留 120s；游戏中不踢出，超时阶段按默认策略代投
4. H5 特有：页面切后台 WS 可能被浏览器挂起，`visibilitychange` 回前台时主动做一次状态拉齐（带本地 version，服务端返回增量或全量）

## 9. 部署拓扑（单机起步）

```
nginx (443, 静态资源 + /api 反代 + /ws 升级 + livekit 信令反代)
├── web 静态文件 (Vite build)
├── server (Fastify, :3000)
├── livekit (:7880 信令, UDP 50000-60000 媒体端口)
├── redis / mysql
```

- LiveKit 媒体走 UDP，需在云安全组放行端口段；受限网络自动回落 TCP/TLS
- 水平扩展路径与小程序版一致：网关按 roomId 一致性哈希 + Redis Pub/Sub；MVP 单实例足够

## 10. 合规注意

- 域名 ICP 备案（个人可办）；如后续加公众号分享卡片再考虑服务号
- 昵称等 UGC 上线前接文本审核（云厂商内容安全 API）
- H5 无平台审核，但微信内传播需避免诱导分享等被封链接的行为（分享引导文案克制）
