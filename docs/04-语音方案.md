# 线上语音对话方案（H5 版）

H5 使用浏览器标准 **WebRTC**，麦克风采集（`getUserMedia`）无需任何平台审批——语音从"资质问题"变成"纯技术问题"，个人开发者可完整落地。

## 1. 方案对比

| 方案 | 延迟 | 成本 | 结论 |
|---|---|---|---|
| A. 自建 LiveKit SFU（开源） | <300ms | 只花服务器钱 | **首选**，预算敏感、完全可控 |
| B. 腾讯云 TRTC Web SDK / 声网 | <300ms | 按用量计费（有免费额度） | 备选，省运维、弱网优化更好 |
| C. P2P Mesh | 低 | 0 | **否决**：10 人局每端 9 路上行，手机带宽/CPU 撑不住 |

### 方案 A：自建 LiveKit（首选）

- 10 人纯音频每路 Opus 约 30-50kbps，一台 2 核 4G / 5M 带宽的轻量服务器可支撑数十个房间
- 游戏服务端用 LiveKit Server SDK 签发 **AccessToken**（JWT），token 中直接声明发布/订阅权限——阶段闭麦与阵营私聊天然由权限模型实现
- 客户端用 `livekit-client`，房间名 = 游戏房间码，纯音频（不发视频）

```
玩家进房 → 游戏服务端校验座位 → 签发 LiveKit AccessToken(带权限)
        → 前端 room.connect(wss://live.域名, token) → 自动发布麦克风音轨
阶段切换 → 服务端调用 LiveKit RoomService API 更新权限/静音
        → 同时 WS 推送 voice.policy 给前端做 UI 同步(麦克风图标状态)
```

## 2. 阶段联动闭麦策略（与游戏状态机绑定）

| 游戏阶段 | 麦克风策略 | LiveKit 实现 |
|---|---|---|
| LOBBY / 组队讨论 | 全员自由发言 | 默认 canPublish=true |
| 夜晚看牌 | 全员强制静音 | RoomService.MutePublishedTrack 全员 |
| 任务出票中 | 全员静音（可配置） | 同上 |
| 刺杀阶段 | 仅邪恶方互相通话，正义方听不到也说不了 | 重签 token：正义方 canPublish=false + 服务端下发指令让正义方端取消订阅邪恶方音轨；或用 track 订阅权限 API 定向控制 |
| 结算 | 全员自由发言 | 恢复权限 |

服务端是唯一权威：闭麦即使客户端被篡改也无效（SFU 侧不转发未授权音轨）。

## 3. 浏览器/微信内兼容性（H5 的主要代价）

| 问题 | 处理 |
|---|---|
| 麦克风授权必须用户手势触发 | 进房后显示「点击开启麦克风」引导按钮，不自动拉起 |
| 必须 HTTPS | 全站 HTTPS + wss，无例外 |
| iOS 微信内置浏览器 | iOS ≥14.3 的 WKWebView 支持 WebRTC；更低版本提示升级或转用系统浏览器打开 |
| 安卓微信 X5 内核 | 基本支持；个别机型 `getUserMedia` 异常时降级为"仅听不说" |
| 切后台/息屏挂起音频 | `wakeLock` 防息屏 + 页面回前台自动重连音轨 + UI 常驻提示"游戏中请保持亮屏" |
| 自动播放限制 | 远端音轨播放绑定在首次用户手势后统一 `audio.play()` |
| 弱网 | Opus 自适应码率；断流 3s 显示该玩家头像"语音中断"角标 |

## 4. 服务端接口

```
POST /voice/token        # 校验用户在房间且在座 → 签发 LiveKit AccessToken(2h)
WS   voice.policy        # 阶段切换推送 { muteAll, publishSeats[], subscribeMatrix? }
```

## 5. 降级链路

1. WebRTC 完全不可用（老旧内核）→ 自动切换**文字快捷短语模式**（游戏功能不受影响）
2. 能听不能说（授权被拒/采集失败）→ 保留收听 + 快捷短语
3. LiveKit 服务不可用 → 全房间提示语音故障，游戏继续

快捷短语作为常驻能力保留（不仅是降级）：部分玩家在不便说话的场合也能参与。

## 6. 内容安全

- 实时语音房为私密朋友局（房间码进入），风险低；上线初期不接语音审核
- 若后续开放公开匹配大厅，再评估接入云厂商音频流审核
