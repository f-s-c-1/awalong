# 开发路线图与工程规划

## 1. 里程碑

### M1 — 可玩 MVP（约 3-4 周）
- [ ] 服务端：NestJS 骨架、微信登录、WS 网关、房间系统（创建/加入/座位/准备）
- [ ] 游戏状态机：默认板子、完整流程（夜晚→组队→投票→任务→刺杀→结算）
- [ ] 小程序端：首页 / 大厅 / 游戏桌面 / 结算 四页
- [ ] 沟通：快捷短语 + 微信群语音引导（无 TRTC）
- [ ] 断线重连、超时代投
- 验收标准：5-10 人真机完整跑通一局，无需口头解释规则

### M2 — 体验完善（约 2 周）
- [ ] 自定义角色板子（莫德雷德/奥伯伦）
- [ ] 结算复盘时间线、战绩持久化与个人战绩页
- [ ] 动效打磨（翻牌、亮票、刺杀）、音效
- [ ] 旁观者模式、分享卡片/小程序码进房

### M3 — 实时语音（依赖企业主体资质，约 2 周）
- [ ] 企业认证 + live 组件类目申请 + TRTC 开通
- [ ] 语音房接入、阶段联动闭麦、刺杀阶段阵营私聊
- [ ] 降级链路与弱网策略

### M4 — 上线运营
- [ ] 内容安全接入（文本昵称审核 `msgSecCheck`、语音审核评估）
- [ ] 压测（目标：单实例 1000 并发房间）、监控告警
- [ ] 提审（类目、隐私协议、用户协议）

## 2. 仓库结构（monorepo）

```
awalong/
├── docs/               # 设计文档（本目录）
├── miniprogram/        # 微信小程序（TypeScript）
│   ├── pages/
│   ├── components/     # seat-ring / role-card / vote-panel / voice-bar
│   ├── store/          # 全局状态(mobx-miniprogram 或自研 event store)
│   ├── services/       # ws.ts / api.ts / voice.ts
│   └── assets/
├── server/             # NestJS 服务端
│   ├── src/modules/    # auth / room / game / voice / gateway
│   └── test/           # 状态机单测(重点：规则判定全覆盖)
└── shared/             # 前后端共享的协议类型定义(消息 type、枚举)
```

## 3. 质量要求

- 游戏状态机必须有单元测试全覆盖：各人数配置的任务判定、5 次否决、第 4 轮双失败票、刺杀分支、超时代投
- 协议类型放 `shared/` 由前后端共同引用，杜绝字段漂移
- 服务端所有阶段流转打审计日志（roomId + version + 事件），线上纠纷可回放

## 4. 待确认决策（开发前需拍板）

1. 小程序主体：是否已有**企业主体**？（决定 M3 语音能否做、以及类目申报路径）
2. 产品申报形态：小游戏类目 vs 普通小程序（社交类目）——影响审核要求与能力边界
3. 服务器：微信云托管 or 自购云服务器（云托管对 WS 支持已可用，运维成本低，推荐）
4. 是否需要账号体系之外的游客模式（微信登录已足够轻，建议不做游客）
